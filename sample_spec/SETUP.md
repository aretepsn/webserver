# sample_spec 설치

`spec/` 폴더를 정본으로 두고 **모든 src 를 spec 에서 만드는 방식**을 다른 프로젝트에 심는 샘플입니다. 웹 · CLI · 데스크톱 · 임베디드 · 라이브러리 등 프로젝트 종류와 관계없이 씁니다.

## 쓰는 법 (사람용)

1. 이 `sample_spec` 폴더를 대상 프로젝트 **루트**에 복사합니다.
2. Claude Code 에서 한 줄 입력합니다.

   ```
   sample_spec/SETUP.md 읽고 진행해
   ```

3. 신규 프로젝트면 질문에 답해 spec 뼈대를 만들고, spec 을 채운 뒤 `/src-init` 으로 src 를 만듭니다.
   진행 중인 프로젝트면 기존 코드에서 spec 을 역으로 작성합니다 — **사람이 검토한 뒤** 커밋하고, 이후로는 spec 을 고치고 `/src-update` 로 반영합니다.

설치 뒤 쓰는 명령:

| 명령 | 하는 일 |
|---|---|
| `/src-init` | spec 만 보고 src 를 처음부터 구현 (`spec/00_시작/04_구현_지시문.md`) |
| `/src-update` | 마지막 반영 뒤 바뀐 spec 만 src 에 반영 (`spec/00_시작/05_구현_지시문_변경시.md`) |

설치가 끝나면 이 `sample_spec` 폴더는 지워도 됩니다. 이후의 기준 문서는 **`spec/README.md`** 입니다.

## 폴더 구성

```
sample_spec/
├─ SETUP.md          ← 이 파일 (설치 진입점)
├─ spec_template/    ← spec/ 로 복사될 뼈대 (README.md + 00_시작/)
├─ commands/         ← .claude/commands/ 로 복사될 명령 2개 (src-init · src-update)
└─ CLAUDE_rules.md   ← 루트 CLAUDE.md 에 덧붙일 규칙
```

---

## 설치 절차 (Claude 용)

아래를 차례대로 수행한다. 각 단계의 결과를 짧게 보고하고, **충돌이나 판단이 필요한 것은 임의로 정하지 말고 묻는다.**
「루트」 는 이 파일이 들어 있는 `sample_spec/` 의 부모 폴더다.

### 1. 사전 점검 (아무것도 바꾸지 않는다)

- 루트가 git 저장소인가. 아니면 `git init` 을 제안한다 — `/src-update` 가 git 으로 바뀐 spec 을 찾으므로 git 이 필요하다. 거절하면 설치는 계속하되 `/src-update` 는 매번 spec 전체를 대조한다는 점을 알린다.
- 충돌 확인:
  - `spec/` 가 이미 있는가 → 있으면 **덮어쓰지 않는다.** ① 기존 spec 을 `spec_old/` 로 옮기고 새로 만들기 ② 기존 spec 에 `README.md` · `00_시작/` 중 없는 것만 더하기 ③ 중단 — 중에서 묻는다.
  - `.claude/commands/` 에 `src-init.md` · `src-update.md` 가 있는가 → 있으면 파일마다 덮어쓸지 묻는다.
  - `CLAUDE.md` 가 있는가 → 있으면 덮어쓰지 않고 뒤에 덧붙인다(3단계).
- 점검 결과를 한 표로 보고한다.

### 2. 프로젝트 상태 판별

- 이미 구현된 코드가 있는지 본다. 코드가 `src/` 에 있다고 넘겨짚지 않는다 — 빌드 · 의존성 파일(`package.json` · `pyproject.toml` · `requirements.txt` · `*.csproj` · `*.sln` · `pom.xml` · `build.gradle` · `go.mod` · `Cargo.toml` · `CMakeLists.txt` · `Makefile` 등)과 소스 파일의 분포로 판단한다.
- 판별 결과를 보고하고 **사용자에게 확인받는다.**
  - **신규** — 구현된 코드가 없거나 버릴 예정
  - **기존** — 지금 코드가 동작하고 있고, 그 동작을 spec 으로 옮긴 뒤 이어서 개발
- 기존이면 **코드 위치**(src 에 해당하는 폴더 · 파일들)도 함께 확인한다. `src/` 가 아니어도 옮기지 않는다 — spec/README 에 실제 위치를 적는다.

### 3. 설치

- `sample_spec/spec_template/` 의 내용을 루트 `spec/` 로 복사한다(1단계에서 고른 방식대로).
- `sample_spec/commands/` 의 두 파일을 루트 `.claude/commands/` 로 복사한다(폴더가 없으면 만든다).
- `sample_spec/CLAUDE_rules.md` 의 `---` 아래 내용을 루트 `CLAUDE.md` 에 덧붙인다(없으면 새로 만든다). 이미 같은 규칙이 있으면 중복해서 넣지 않는다.

### 4. spec 채우기

방금 복사한 spec/ 뼈대(README.md · 00_시작/)를 2단계 판별 결과(신규 / 기존)로 이 프로젝트에 맞게 채운다. **src 는 한 줄도 바꾸지 않는다.**

**4-1. 프로젝트 파악**
- 신규: 사용자에게 묻는다(한 번에 몰아서, 모르는 것은 「미정」 으로 받는다).
  ① 한 줄 목적과 누가 쓰나 ② 종류(웹 · API 서버 · CLI · 데스크톱 · 모바일 · 임베디드/펌웨어 · 라이브러리/SDK · 배치/데이터 파이프라인 · 기타)
  ③ 언어 · 프레임워크 · 주요 의존성 ④ 데이터 저장(DB · 파일 · 없음) ⑤ 외부 연동(API · 장치 · 파일 형식)
  ⑥ 시험 방법(자동 시험 도구 · 사람이 하는 시험) ⑦ 배포 · 실행 환경 ⑧ 이미 있는 자료(요구서 · 화면 초안 · 회의록 등)
- 기존: 코드를 읽어 위 ①~⑧ 을 스스로 채우고, 추정한 것은 추정이라고 표시해 보고한다. 빌드 · 실행 · 시험 명령은 실제로 돌려 확인한다(돌리지 못하면 「미확인」).

**4-2. 폴더 구성 설계**
- 00_시작 은 고정이다(01_개요 · 02_정책 · 03_정책_결정기록 · 04_구현_지시문 · 05_구현_지시문_변경시). 04 · 05 는 범용 지시문이므로 고치지 않는다.
- 10 이후 폴더는 프로젝트 종류에 맞게 정한다. **번호 = src 를 만드는 차례**(먼저 만들어야 하는 것이 앞). 50_시험 · 90_운영 은 되도록 둔다. 예:

  | 종류 | 10 | 20 | 30 | 40 | 50 | 90 |
  |---|---|---|---|---|---|---|
  | 웹 | 설정 | 데이터 | 공통모듈 | 화면 | 시험 | 운영 |
  | API 서버 | 설정 | 데이터 | 공통모듈 | API | 시험 | 운영 |
  | CLI | 설정 | 데이터/파일형식 | 공통모듈 | 명령 | 시험 | 배포 |
  | 데스크톱 · 모바일 | 설정 | 데이터 | 공통모듈 | 화면 | 시험 | 배포 |
  | 임베디드 | 하드웨어 · 핀 | 통신 프로토콜 | 드라이버 · 공통 | 기능 · 상태기계 | 시험 | 빌드 · 굽기 |
  | 라이브러리 | 설정 · 빌드 | 자료형 | 내부 모듈 | 공개 API | 시험 | 배포 · 버전 |
  | 배치 · 데이터 | 설정 | 입력 · 출력 형식 | 공통 변환 | 작업(잡) | 시험 | 운영 · 스케줄 |

  표는 예시일 뿐이다. 필요 없는 폴더는 두지 않고, 필요하면 더한다(예 60_연동).
- 설계안(폴더 · 각 폴더에 들어갈 문서 · 대응 src 위치)을 먼저 보고하고 승인받은 뒤 만든다.

**4-3. 작성**
- spec/README.md 의 <...> 자리를 모두 채운다 — 특히 「구성」 표(폴더 · 무엇 · 대응 src)와 「기술 · 실행」(빌드 · 실행 · 시험 명령). `/src-init` · `/src-update` 는 이 두 절에 기대어 동작한다.
- 폴더마다 README.md 를 두어 그 폴더에 무엇을 어떤 꼴로 적는지 밝힌다. 상세 문서 한 장의 꼴은 「앞부분 = 무엇 · 구성 · 흐름과 규칙(사람 말) / `---` 아래 = 구체 명세(입력 · 출력 · 오류 · 코드 위치 · 시험)」 로 한다.
- 신규:
  - 01_개요 는 받은 답으로 초안을 쓰고, 02_정책 · 상세 문서는 **제목과 적을 거리만** 둔다(내용을 지어내지 않는다). 모르는 것은 03_정책_결정기록 「확인 대기」 에 올린다.
  - 사용자가 준 요구 자료가 있으면 그것을 근거로 채우고, 근거를 문서에 적는다.
- 기존:
  - **현행 동작을 그대로** 적는다(바람직한 동작이 아니라 지금 동작). 「코드」 열은 `파일 함수명` · 줄 번호 없음.
  - 버그로 보이거나 앞뒤가 맞지 않거나 의도를 알 수 없는 동작은 02_정책 에 규칙으로 굳히지 말고 03 「확인 대기」 에 「현행 동작 · 왜 의심스러운가」 로 올린다.
  - 기존 시험이 있으면 50_시험 에 인수기준(전제 · 행위 · 기대)으로 옮겨 적고 시험 코드 위치를 잇는다. 시험이 없으면 인수기준 문서만 쓰고, 시험 코드를 만들지는 묻는다.
  - spec/README.md 맨 위에 「현행 src 에서 역작성 — 사람 검토 전」 을 적는다(검토가 끝나면 사용자가 지운다).
  - 양이 많으면 폴더 단위로 나눠 쓰고, 폴더 하나가 끝날 때마다 보고한다.

### 5. 마무리

- 보고: ① 설치한 파일 목록 ② 판별 결과(신규 / 기존) ③ 작성한 spec 파일 목록 ④ 사람이 검토해야 할 곳 ⑤ 다음에 할 일
  - 신규: 「spec 을 채운 뒤 `/src-init`」
  - 기존: 「역작성한 spec 을 검토 → 확인 대기 항목을 결정 → 커밋. 이후로는 spec 을 고치고 `/src-update`」
- 커밋 제안(커밋은 사용자가 결정):
  - 신규: `spec: 최초 뼈대 작성`
  - 기존: 검토가 끝난 뒤 `spec 반영: 현행 src 기준 spec 역작성` — 이 메시지가 `/src-update` 의 첫 기준점이 된다. **검토 전에는 이 메시지로 커밋하지 않는다**(검토 전 spec 이 기준점이 되면 안 됨).
- `sample_spec/` 폴더를 지울지 묻는다.
