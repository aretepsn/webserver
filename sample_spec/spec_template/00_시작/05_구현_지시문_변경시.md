# spec 반영 프롬프트 (변경시)

`spec/` 문서를 **고친 뒤** 그 변경만 src 에 반영할 때 쓰는 지시문입니다. Claude Code 에서는 `/src-update` 로 부릅니다. 바뀐 곳은 사람이 적지 않고 **프롬프트가 git 으로 찾습니다** — 그러려면 src 를 마지막으로 맞춘 시점이 커밋으로 남아 있어야 합니다(아래 「쓰는 차례」).

이 파일도 04 와 같이 **범용 지시문**이라 고치지 않습니다. 프로젝트마다 다른 것은 [spec/README.md](../README.md) 에 적습니다.

---

```
spec/ 가 정본이다. spec 이 바뀌었으니 바뀐 곳만 src 에 반영하라. src 를 새로 만들지 말고, 바뀌지 않은 spec 에 해당하는 코드는 건드리지 않는다.
작업 규칙 · 기술 · 시험 · 진행 규칙은 spec/00_시작/04_구현_지시문.md 와 같다 — 그 파일과 spec/README.md 를 먼저 읽고 이 지시를 따른다. 단 04 의 「src 를 모두 지우고 새로 만든다」 는 이 작업에 적용하지 않는다.

[바뀐 곳 찾기 — git 으로]
1. 기준점 = 시험까지 통과시켜 src 를 spec 에 맞춘 것이 확인된 커밋. 찾는 차례:
   - 사용자가 기준점을 주었으면 그것을 쓴다.
   - 커밋 메시지 첫 줄이 「spec 반영: …」 인 가장 최근 커밋: git log --oneline -- spec <src 위치> (개수를 제한하지 않는다)
   - 없으면 **기준점을 모르는 것으로 보고 spec 전부를 대조 대상으로 삼는다** — src 를 마지막으로 바꾼 커밋으로 넘겨짚지 않는다(그 커밋이 반영과 무관한 수정이면 아직 구현하지 않은 spec 이 비교에서 빠진다). 이때 먼저 「기준점을 찾지 못해 spec 전체를 봅니다」 를 보고한다.
   - git 저장소가 아니면 spec 전체를 대조하고 그 사실을 보고한다.
2. 그 커밋 이후 spec 에서 바뀐 파일: git diff --stat <기준점>..HEAD -- spec  +  git status --short spec (아직 커밋하지 않은 변경도 포함)
3. 파일마다 무엇이 바뀌었는지 본다: git diff <기준점> -- <파일>. 새 파일은 전체를 읽는다.
4. 찾은 목록을 먼저 보고한다 — 「어느 파일의 어느 절이 어떻게 바뀌었고, src 의 어느 파일에 영향이 있다」 를 표로. 영향받는 src 는 spec/README 「구성」 의 대응 src 에서 시작해 실제 코드를 따라가 찾는다. 영향이 없는 변경(문구 · 설명만)은 「반영할 것 없음」 으로 적는다.
   spec/README 「변경으로 보지 않는 것」 에 적힌 파일(제안서 · 생성물 · 결과물 · 사람의 실행 기록)은 변경으로 보지 않는다.

[반영]
- 반영 범위는 **바뀐 요구사항을 구현하고 검증하는 데 필요한 파일 전부**다. 문서 하나가 바뀌었다고 그 대응 파일 하나만 보지 않는다 — 공통 로직 · 공통 부품 · 설정 · 시험에도 나뉘어 있을 수 있다. 공통 부품 문서가 바뀌었으면 그것을 쓰는 단위 전부를 본다.
- 설정 · 구조(데이터 구조 · 스키마 · 파일 형식 · 프로토콜 등)가 바뀌었으면 spec/README 「프로젝트 고유 지시」 와 운영 문서의 절차를 따른다. 절차가 없고 기존 자료 · 운영 환경에 영향이 있으면 먼저 물어라.
- **정책(02_정책 · 03_정책_결정기록)이 바뀌었으면 함께 점검한다** — 그 규칙을 푼 상세 문서와 시험 항목. 어긋나면 정책이 정본이다(spec/README 「서로 어긋날 때」).
- 03_정책_결정기록 「확인 대기」 에서 항목이 지워지고 결론이 적혔으면 그 결론대로 동작을 바꾼다. 아직 표에 있는 항목은 현행 유지.
- 고친 단위는 그 문서의 규칙을 한 줄씩 짚어 src 의 어디에 구현했는지 대 보고, 대지 못한 줄이 있으면 보고한다(시험 통과와 별개).
- 새 규칙 · 바뀐 규칙에 대응하는 시험이 없으면 인수기준과 시험을 함께 더한다.
- spec 에 없는 기능은 더하지 않는다. 바뀐 spec 이 두 가지로 읽히면 정하지 말고 먼저 물어라.

[시험 · 보고]
- 「기술 · 실행」 의 시험 명령으로 **전부** 돌린다 — 바뀐 것과 무관한 시험도 돌려 다른 곳이 깨지지 않았음을 보인다. .harness/작업목록.md 에 이번 변경분을 항목으로 더하고 끝낼 때마다 [x].
- 보고: ① git 으로 찾은 변경 목록(기준점 커밋 포함 · 못 찾았으면 그 사실) ② src 에서 고친 파일과 무엇을 고쳤는지 ③ 시험 결과(통과 · 실패 · 미검증) ④ 반영하다 spec 을 고친 곳 「어느 파일 어느 절」 ⑤ 시험 기대값을 바꾼 것이 있으면 번호와 이유 ⑥ 사람이 하는 시험이 있으면 이번 변경으로 다시 봐야 할 항목(고친 단위만 · 공통 부품을 고쳤으면 그것을 쓰는 단위 전부).
- 끝나면 커밋 메시지 첫 줄을 「spec 반영: <한 줄 요약>」 으로 해서 spec 과 src 를 함께 커밋하도록 제안한다(커밋은 사용자가 결정) — 다음 변경 때 이 커밋이 기준점이 된다.
```

---

## 쓰는 차례

1. spec 문서를 고친다(문서가 곧 결정). 새 규칙에는 인수기준 항목과 시험을 함께 더한다.
2. `/src-update` 를 입력한다. 바뀐 곳은 적지 않는다 — 프롬프트가 git 으로 찾아 먼저 목록을 보고한다.
3. 목록이 맞으면 진행시키고, 시험이 모두 통과하면 `spec 반영: …` 으로 spec 과 src 를 함께 커밋한다. 이 커밋이 다음 변경의 기준점이다.

## 기준점이 없을 때

src 를 한 번도 커밋하지 않았거나 spec 과 src 를 따로 커밋해 왔다면 기준점을 잘못 잡을 수 있습니다. 그때는 기준점을 직접 줍니다.

```
/src-update 기준점 커밋은 <해시> 다. 그 뒤로 바뀐 spec 만 본다.
```

## 이 프롬프트가 정해 주는 것 (spec 밖의 것)

| 구분 | 왜 spec 에 없나 |
|---|---|
| 바뀐 곳을 git 으로 찾는 방법 · 기준점 규칙 | 작업 방식 — spec 은 「무엇」 만 적고 「어떻게 찾나」 는 정하지 않음 |
| 바뀐 곳만 고치고 나머지는 건드리지 않는 범위 규칙 | 사용자의 진행 규칙 |
| 변경 목록을 먼저 보고하고 진행하는 차례 · 커밋 메시지 꼴 | 사용자의 진행 규칙 |
