# spec 반영 프롬프트 (처음 구현)

`spec/` 폴더만 보고 src 를 **처음 구현할 때** 쓰는 지시문입니다. Claude Code 에서는 `/src-init` 으로 부릅니다. 그 뒤로 spec 이 바뀌어 바뀐 곳만 반영할 때는 [05_구현_지시문_변경시.md](05_구현_지시문_변경시.md)(`/src-update`)를 씁니다.

이 파일은 **모든 프로젝트에 공통인 범용 지시문**이라 고치지 않습니다. 프로젝트마다 다른 것(기술 · 폴더 · 명령 · 고유 규칙)은 [spec/README.md](../README.md) 에 적고, 지시문은 그것을 읽어 따릅니다.

---

```
spec/ 가 정본이다. 이 폴더만 보고 src 를 구현하라. spec 에 없는 기능은 더하지 않는다.
구현하다 spec 과 어긋나거나 빠진 것이 나오면 코드를 임의로 정하지 말고 나에게 물어라. 결정은 spec 문서를 고치는 것으로 남긴다(spec 이 곧 결정).

[먼저 읽을 것]
1. spec/README.md — 전부 읽는다. 특히
   「구성」: 읽는 차례 = 만드는 차례 · 폴더마다 대응 src 위치
   「기술 · 실행」: 언어 · 프레임워크 · 의존성 · src 위치 · 빌드 · 실행 · 시험 명령
   「프로젝트 고유 지시」: 이 지시문에 더해 지킬 것 — 이 지시문과 같은 무게로 따른다
   「서로 어긋날 때」: 문서끼리 어긋날 때의 정본 차례
2. spec/00_시작/ 01_개요 · 02_정책 · 03_정책_결정기록
3. 「구성」 표의 차례대로 나머지 폴더 — 폴더마다 README.md 가 있으면 먼저 읽는다
README 의 <...> 자리가 비어 있거나 「기술 · 실행」 이 채워져 있지 않으면 시작하지 말고 알린다.

[기술]
- 「기술 · 실행」 에 적힌 기술만 쓴다. 다른 기술 · 의존성을 더하려면 먼저 말하고 승인받는다.
- 설정 · 비밀값(접속 정보 · 키 등)은 코드에 적지 않고 README 에 적힌 설정 파일에서 읽는다.

[작업 방식]
- 「기술 · 실행」 의 src 위치(spec 을 반영해 만들어지는 부분)는 모두 지우고 새로 만든다 — 있던 파일을 그대로 두거나 "같겠지" 하고 넘겨짚지 않는다.
  단, 지우기 전에 지울 목록을 보고하고 승인받는다. spec 에 대응이 없는 파일(사람이 따로 둔 자료 등)이 있으면 목록에 표시해 따로 묻는다.
- spec 에 없거나 두 가지로 읽히는 것은 정하지 말고 먼저 물어라. 03_정책_결정기록 「확인 대기」 항목은 내가 결정하기 전까지 현행 동작(없으면 가장 단순한 동작)을 따르고, 보고에 그 사실을 적는다.
- 공통 부품(여러 곳이 쓰는 것)을 먼저 만들고 그것을 쓰는 단위를 나중에 만든다 — 「구성」 의 차례가 그 차례다.
- 단위(화면 · 명령 · API · 기능 등) 하나를 만들 때마다 그 문서의 규칙을 **한 줄씩 짚어 src 의 어디에 구현했는지 대 보고**, 대지 못한 줄이 있으면 보고하라. 시험이 모두 통과해도 이 대조를 건너뛰지 않는다.
- 한 단계가 끝날 때마다 무엇을 만들었고 무엇을 확인했는지 **실제 실행 결과로** 보고하라. 끝에는 「기술 · 실행」 의 실행 명령으로 한 번은 실제로 띄워 · 돌려 본다.
- 작업 폴더는 이 프로젝트 루트 하나다. 다른 폴더는 건드리지 않는다.

[시험]
- 「기술 · 실행」 의 시험 명령으로 전부 통과해야 한다. 50_시험(또는 README 가 가리키는 시험 폴더)의 인수기준 항목마다 같은 기대를 확인하는 시험이 있어야 한다 — 없으면 만든다.
- **시험의 기대값을 바꾸면 반드시 보고한다** — 무엇을 어떻게 왜 바꿨는지. 기대값을 구현에 맞춰 조용히 바꾸면 잘못된 구현이 정답이 된다. 돌리는 방법(절차 · 선택자 등)만 고친 것은 보고하지 않아도 된다.
- 환경이 없어 못 본 항목은 통과로 바꾸지 말고 「미검증」 으로 남긴다.
- 사람이 하는 시험 문서가 있으면, src 를 새로 만들었으므로 지난 실행 기록은 무효라고 보고 마지막에 「사람이 하는 시험을 처음부터 다시 해야 합니다」 를 적는다(기록 자체는 지우지 않는다).

[진행 규칙]
- 시작할 때 .harness/작업목록.md 를 만든다 — 「구성」 의 차례를 단계로 나눠 번호 · 내용 · 대상 · 처리 [ ] 칸을 두고, 한 항목을 실제로 끝낼 때마다 [x] 로 바꾼다.
- spec 과 어긋나 내가 결정한 것은 spec 문서에 고쳐 넣고(03_정책_결정기록 「확인 대기」 에서 지우고 결정 기록 · 02_정책 · 상세 문서에 결론), 보고에 「spec 어느 파일 어느 절을 고쳤다」 를 적는다. 문서의 「코드」 열은 `파일 함수명` 으로 적고 줄 번호는 적지 않는다.
- 보고: ① 만든 src 파일 ② 시험 결과(통과 · 실패 · 미검증) ③ 대조하지 못한 규칙 ④ spec 을 고친 곳 ⑤ 시험 기대값을 바꾼 것과 이유 ⑥ 확인 대기 때문에 현행 · 단순 동작으로 둔 것.
- 끝나면 커밋 메시지 첫 줄을 「spec 반영: <한 줄 요약>」 으로 해서 spec 과 src 를 함께 커밋하도록 제안한다(커밋은 사용자가 결정) — 다음 /src-update 의 기준점이 된다.
```

## 이 프롬프트가 정해 주는 것 (spec 밖의 것)

| 구분 | 왜 spec 에 없나 |
|---|---|
| 묻고 진행하는 작업 방식 · 작업목록 · 보고 꼴 | 사용자의 진행 규칙 |
| 확인 대기 항목을 어떻게 다룰지 | 결정 전까지 현행 유지라는 작업 규칙 |
| 기대값을 바꿀 때 보고 | 시험이 정답을 지키게 하는 작업 규칙 |
| 기술 · 명령 · 고유 규칙 | 프로젝트마다 달라 **spec/README.md** 에 둠 |
